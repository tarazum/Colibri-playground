## Finding R-001 — Qwen3.6 build target is incorrect

**Severity:** High  
**Status:** Open  
**Affected files:** `docs/experiment_plan.md`, `docs/open_items.md`, `LOG.md`

The current plan states that v1.12.0 uses a single unified `colibri.exe` engine for Qwen3.6 and proposes:

```text
make colibri.exe CUDA_DLL=1 ARCH=native
```

This is not correct for the pinned v1.12.0 source.

At commit `dcd73832f...`, the Makefile contains a dedicated Qwen3.6 target:

```text
qwen36$(EXE): ...
```

and explicitly documents the Windows CUDA form:

```text
make qwen36.exe CUDA_DLL=1
```

`colibri.exe` is the core GLM-family engine. Qwen3.6 uses the separate `qwen36.exe` engine artifact.

### Required correction

Use the Qwen3.6 target for the Windows CUDA build. Expected outline:

```text
make cuda-dll CUDA_ARCH=sm_120
make qwen36.exe CUDA_DLL=1 ARCH=native
```

Verify the exact dependencies/output on the pinned source before the benchmark, then require the Qwen3.6 CUDA startup banner as proof that the correct binary is running.

### Evidence

Pinned upstream source:

- `c/Makefile`
- `c/family_registry.py` — Qwen3.6 has `engine_artifact="qwen36"` and `build_target="qwen36"`

## Finding R-002 — `IDOT_GS=1` was attributed to the wrong engine

**Severity:** High  
**Status:** Open  
**Affected files:** `docs/experiment_plan.md`, `docs/open_items.md`, `LOG.md`

The repository currently records `IDOT_GS=1` as something that should be enabled for the Qwen3.6 gs64 benchmark.

The variable exists in `c/colibri.c`, where it controls grouped planar IDOT behavior for the core Colibrì/GLM engine.

Qwen3.6 does not use `c/colibri.c` as its inference engine. It uses `c/qwen36.c`.

The Qwen3.6 source independently supports grouped-scale experts:

- it reads `expert_gs` from `qwen36_meta.json`
- it has grouped-scale expert computation paths
- it reports `[qwen36] group-scaled experts: gs=N`

Therefore:

- the conclusion that the gs64 container is supported by v1.12.0 is valid
- the conclusion that Qwen3.6 benchmark runs should set `IDOT_GS=1` is not supported by the Qwen3.6 source

### Required correction

Remove `IDOT_GS=1` from the Qwen3.6 benchmark recipe unless a Qwen3.6-specific source path is found that reads it.

Runtime confirmation should instead require:

```text
[qwen36] group-scaled experts: gs=64
```

plus a clean `doctor --deep` / successful model load.

## Finding R-003 — current benchmark runner does not match the Qwen3.6 execution path

**Severity:** High  
**Status:** Open  
**Affected file:** `tools/run_bench.py`

The runner is intentionally marked as incomplete, which is good. Its current example command is:

```text
coli.cmd chat --model {model} --prompt-file {prompt_file}
```

This does not match v1.12.0:

- `coli chat` does not expose a `--prompt-file` option
- Qwen3.6 has `has_cli_adapter=False`
- upstream explicitly routes Qwen3.6 users to `coli chat` or `coli serve`
- spawning a fresh chat/server per sample would also contaminate or destroy the intended warm-cache experiment semantics

### Recommended design

Use one persistent:

```text
coli serve --model <model>
```

and drive benchmark requests through the OpenAI-compatible HTTP API.

This gives several advantages:

- model load time is separated from request latency
- warm-process expert state can be measured intentionally
- KV reuse can be tested correctly
- the same transport can later be used for Brio/API integration experiments
- CPU and CUDA test harnesses can use the same request path

The runner should save:

- raw request/response
- server log
- wall time
- completion tokens
- prompt tokens when reported
- decode tok/s from the server/DONE frame
- cache hit rate when reported
- HTTP status/error details

Do not cite regex-derived metrics until the parser has been validated against the first real server log.

## Finding R-004 — cold/warm and deterministic benchmark protocol needs to be explicit

**Severity:** Medium  
**Status:** Open  
**Affected files:** `docs/experiment_plan.md`, benchmark tooling

Qwen3.6 chat sampling is not deterministic by default. Colibrì documents:

- `COLI_TEMP=0` = greedy/argmax
- unset seed = clock/PID based randomness

For performance comparison, output length and routing behavior should not drift because sampling changed between runs.

The current plan also uses the word "warm" in several places without fully separating process warmth from persisted expert heat.

### Required benchmark protocol

Use deterministic generation for performance runs:

```text
temperature = 0
fixed max_tokens
same prompt bytes
same model revision
same power mode
```

Define three different states:

### Cold

- new server process
- no existing `HEAT_FILE`
- no reused KV/session state

### Warm-process

- same running server
- prior workload has already populated runtime expert heat/residency
- no process restart

### Warm-persisted

- stop cleanly so `HEAT_FILE` is saved
- restart the server
- load the same `HEAT_FILE`
- rerun the same workload

This distinction is important because Colibrì explicitly loads and saves expert heat through `HEAT_FILE`.

Each result JSON should identify the state explicitly, not only use a generic `mode: warm-cache`.

## Finding R-005 — code benchmark prompt has one ambiguity

**Severity:** Low  
**Status:** Open  
**Affected file:** `prompts/p3_code.txt`

The prompt asks for tests covering touching half-open intervals:

```text
[1,2) and [2,3)
```

but does not explicitly state the expected behavior.

For half-open intervals these intervals do not overlap, but some interval-merging implementations intentionally merge adjacent ranges.

Because this prompt is intended to be mechanically checkable, the expected semantics should be explicit.

### Recommended correction

Add:

```text
Touching half-open intervals are not overlapping and must remain separate.
```

After the first benchmark uses the existing prompt, do not edit it in place. If no benchmark has used it yet, it is safe to clarify the existing file now.

## Readiness assessment

### Phase 0

**Assessment: strong / nearly complete.**

Environment and toolchain preparation are sufficient to proceed once the technical assumptions above are corrected.

### Benchmark harness

**Assessment: not ready for authoritative measurements yet.**

The main blocker is not code quality; it is execution-path correctness. The harness was written before the real Qwen3.6 CLI/server behavior had been fully validated.

### Recommended next sequence

1. Correct R-001 and R-002 in the plan/open items/journal.
2. Convert the benchmark harness to a persistent `coli serve` + HTTP client model.
3. Define deterministic cold / warm-process / warm-persisted modes.
4. Clarify p3 touching-interval semantics.
5. Finish the Qwen3.6 container download.
6. Run `doctor --deep` and verify `gs=64`.
7. Build CPU/Qwen3.6 correctly.
8. Capture one real server log and finish the metric parser.
9. Only then begin CPU/CUDA benchmark series.

No CPU/CUDA performance number should be treated as valid until items 1-4 are closed.
