# Phase 12 brief — GLM-5.3-Flash (321B) on the laptop: feasibility, not speed

Status: BACKLOG (owner: «будем мати заділ»; say «починай» to execute)
Date drafted: 2026-09-26 · Plan ref: experiment_plan §16 · Feeds:
big-model-hardware-notes.md (replaces extrapolations with measurements)
· final_results review triggers.

## Ціль

Технічна здійсненість і навчання: чи «спитай велетня один раз» реально на
цьому ноутбуці (64 GB RAM, RTX 5070 8 GB, один NVMe), і яким числам це
відповідає. Єдиний домовлений формат користі — one-shot verdict/план
(Brio), не розмова.

## Факти upstream (перевірені в їхньому коді/доках)

- Модель: GLM-5.3-Flash, 321B total / 40B active, vision (не наша ціль);
  джерело `zai-org/GLM-5.3-Flash`; рушій `glm53` (`make -C c glm53`);
  model id `glm-5.3-flash-colibri`; їхні доки: docs/glm53-flash.md.
- Контейнер ~195 GB, int4-gs64 експерти + BF16 dense (пріcision —
  вибір при завантаженні). Конвертація ЛОКАЛЬНА і ОДНОПРОХІДНА,
  шарда-за-шардою: `python3 tools/convert_glm53.py --outdir <dir>
  --min-free-gb 30` — качає і конвертує одночасно → пік диска ≈ 195 GB
  + один шард + буфер, а НЕ повний BF16-оригінал.
- RAM-гайд: від 25 GB (12 GB ваги int4 + expert cache) — наші 64 GB
  дають запас на heat-кеш.

## Зрізи

- **S1 Білд**: `build_cpu.bat glm53.exe` → смок; потім `cuda-dll` +
  `glm36...` — ні, `glm53.exe CUDA_DLL=1` (тір для стовбура; авто через
  `--auto-tier`, банер-доказ як завжди).
- **S2 Конвертація**: фоново, старт-нотатка в LOG, `--min-free-gb 30`;
  вільно ~443 GB → після ~195 GB лишається ~240 GB (моніторити!).
  Артефакт: лог конвертації + розмір у results/phase12/.
- **S3 Smoke**: `coli doctor` → одна КОРОТКА генерація (TTFT
  очікуємо в хвилинах — це нормально) + телеметрія RAM/VRAM/disk
  (nvidia-smi логер + Task Manager working set скриптом).
- **S4 Brio-вердикт** — головний тест цінності: 5-10 кейсів із
  prompts/brio_cases.json (state скоротити), normalize вже чесний
  (`sum` — наш #1753). Очікування: хвилини на вердикт → фон.
- **S5 Тепло для glm53**: що в цього рушія є замість qwen36 HEAT_FILE;
  чи наш stdin-drain фікс (#1734) щось зберігає на виході; дельта
  warm-restart, якщо механізм існує.
- **S6 Числа → висновки**: results/phase12/ + оновити extrapolations у
  big-model-hardware-notes.md; матеріал для review-тригерів вердикту
  LAB ONLY (чи «велика модель на ноуті» — реальна ніша).
- **S7 Чистка**: контейнер — ТИМЧАСОВИЙ; після зняття чисел видалити
  `C:\Models\glm53_flash_i4` (+ heat/KV-файли, якщо з'являться) і
  повернути диск. Артефакт фази — числа, не модель.

## Дискова арифметика (стан на 2026-09-26: 378 GB вільних)

- Пік конвертації ≈ 195 ГБ контейнер + один шард оригіналу (~5–8 ГБ,
  качається-конвертується-викидається пошардно) + guard 30 ГБ ≈ **235 ГБ
  піку, ~140 ГБ запасу** — влазить.
- Після конвертації: ~183 ГБ вільних — робоче, але фонових великих
  завантажень більше НЕ запускати до кінця фази.
- Після S7: повертається до ~378 ГБ.

## Не-цілі

Інтерактивна швидкість; якісні скріни; глибокий KV-reuse (у glm53 свій
гейт — окрема історія, див. issue #1759); vision; CUDA-тюнінг понад
авто; GLM-5.2 744B; Kimi K3.

## Критерій закриття

Виміряні (JSON у results/phase12/): cold decode tok/s, TTFT на короткому
і середньому промпті, ≥1 Brio-вердикт з латентністю, RAM/VRAM/disk
профіль, heat-дельта (або «механізму нема» як чесний результат) +
оновлені висновки в hardware-notes. Без «здалося швидким» — тільки числа.

## Ризики й охоронні правила

- Диск: пік ~230-250 GB з ~443 вільних — стежити, не запускати
  паралельно інші завантаження (стале правило: одне велике за раз).
- Час: конвертація і префіли — години; тільки фон + старт-нотатки;
  перевірка АРТЕФАКТОМ (розмір/банер/JSON), не кодом виходу.
- Фоновий I/O гасити під час замірів (диск один, спільний з ОС).
- Терміки тривалого I/O — не марафон GPU, а диск+CPU; спостерігати.
- Перед стартом: перечитати FINDINGS (відкритих, що стосуються, нема:
  FN-006 — український токенайзер gs64, не блокер; #1759 — не-ціль тут).
