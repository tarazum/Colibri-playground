# LESSONS_LEARNED — Colibri-playground

Формат: `LL-NNN | дата | Контекст → Що сталося → Урок → Зміна`. Запис тим самим
днем, коли знайдено корінь (AGENTS.md). Універсальні уроки промоутяться в
крос-проектний плейбук `C:\projects\playbook` (PB-NNN + back-link тут);
контракт — у README плайбука. Перед кожним брифом перечитувати цей журнал
і INDEX плайбука.

### LL-001 | 2026-09-21 | Коди виходу брешуть — доводь артефактом
- **Контекст:** встановлення тулчейну через winget у фоновому ланцюгу.
- **Що сталося:** winget повідомив VS Build Tools «Installer failed» (VS_EXIT=6), але C++ workload виявився уже встановленим і цілим; водночас `make`-фейл сховався за exit 0, бо останньою командою пайпа була `tail`.
- **Урок:** код виходу інсталятора/пайпа — не доказ. Доказ — артефакт: бінарник запускається, версія друкується, смок проходить.
- **Зміна:** `tools/toolchain_smoke.bat` як пост-інсталяційна гребля; у білд-батах `|| exit /b`; у фонових задачах лог пишеться у файл напряму. → **PB-067**

### LL-002 | 2026-09-21 | Git Bash їсть лапки/бекслеші cmd — тимчасовий .bat
- **Контекст:** запуск vcvars64/make/nvcc з Git Bash.
- **Що сталося:** `cmd //c 'call "C:\..." && ...'` передає їдені лапки (`\"`) у cmd; `tools\\file.bat` колапсує в `toolstoolchain.bat`.
- **Урок:** складні команди Windows з лапками/шляхами з Git Bash не передаються наосліп.
- **Зміна:** патерн «temp .bat з прямим шляхом» для всього, що складніше одного слова (те саме правило вже було в IDENN — підтвердилось). → **PB-068**

### LL-003 | 2026-09-21 | MSYS2: make у usr\bin, gcc у mingw64\bin
- **Контекст:** перша CPU-збірка colibri.
- **Що сталося:** `make` знайшовся, `gcc` — ні (`gcc: No such file or directory`), збірка впала.
- **Урок:** у MSYS2 інструменти живуть у різних під-деревах; PATH мусить містити ОБИДВІ папки.
- **Зміна:** `build_cpu.bat`/`build_cuda.bat` ставлять `mingw64\bin` + `usr\bin` (+ CUDA bin) разом.

### LL-004 | 2026-09-21/22 | Документація описує еталонну ціль — звіряй свою
- **Контекст:** docs/windows.md upstream каже `make colibri.exe`.
- **Що сталося:** у кожної модельної родини свій бінарник; наш — `qwen36.exe`. Я «виправив» план на colibri.exe і мав правити назад (FN-003).
- **Урок:** build-документация описує ОДИН випадок; для своєї конфігурації звіряти ціль з самим Makefile/реєстром.
- **Зміна:** правило в open_items/плані: ціль збірки звіряти з `c/Makefile`, не тільки з docs.

### LL-005 | 2026-09-22 | Порада про env-перемикач — від grep по КОНКРЕТНОМУ файлу
- **Контекст:** порадив `IDOT_GS=1` для qwen36-бенчмарків.
- **Що сталося:** змінну читає тільки GLM-рушій (colibri.c); qwen36.c має власні ручки (QWEN_EXPERT_KERNEL, IDOT). Порада була no-op; зловив зовнішній рев'ю (R-002, FN-005).
- **Урок:** у кодових базах з багатьма sibling-модулями спільний заголовок ≠ спільна поведінка; env-порада мусить виходити з grep по модулю, який РЕАЛЬНО виконується.
- **Зміна:** протокол: перед порадою про перемикач — grep по конкретному рушію/модулю + банер у рантаймі як доказ.

### LL-006 | 2026-09-22 | Тихий fallback без прапорця — вимагай банер-доказ
- **Контекст:** перший CUDA-прогін сервера.
- **Що сталося:** `coli serve` без `--auto-tier` МОЛЧА працює CPU-шляхом — жодного попередження; розібрався лише за відсутністю банера `[CUDA] device 0:`.
- **Урок:** якщо режим має доказовий рядок у логу — його відсутність і є аларм; «працює» ≠ «працює в очікуваному режимі».
- **Зміна:** харнес має `--auto-tier`; у протоколі — обов'язкова перевірка банера кожного прискореного прогону. → **PB-069**

### LL-007 | 2026-09-22 | Warm-стан бенчмарків вимагає персистентного процесу
- **Контекст:** перший варіант бенчмаркера (новий процес на семпл).
- **Що сталося:** кожен семпл був би «холодним»; семантика warm-cache знищувалась дизайном (зловив рев'ю R-003).
- **Урок:** коли об'єкт вимірювання — стан ПРОЦЕСУ, харнес тримає процес живим, а стан змінює протоколом (cold/warm-process/warm-persisted).
- **Зміна:** `tools/bench_serve.py`: один persistent сервер + HTTP, теги станів. → **PB-070**

### LL-008 | 2026-09-22 | Детермінізм бенчмарка задається ЯВНО в запиті
- **Контекст:** порівняння CPU/CUDA прогонів.
- **Що сталося:** сервер OpenAI-сумісного API має температуру 0.7 за замовчуванням (коли запит її не несе) — довжина виходів і роутинг експертів дрейфували б між прогонами.
- **Урок:** sampling-параметри не «спадають» детерміновано; кожен бенчмарк-запит мусить явно нести temperature=0 (+ фіксований max_tokens).
- **Зміна:** R-004 протокол у плані; побічний доказ — ідентичні виходи cold/warm. → **PB-071**

### LL-009 | 2026-09-22 | Windows: terminate() ≠ «чисто»; гілляне дерево гаситься не вся
- **Контекст:** спроба зберегти HEAT_FILE коректним завершенням сервера.
- **Що сталося:** `Popen.terminate()` на Windows = TerminateProcess (teardown не виконується); CTRL_BREAK з окремою групою процесів коректно гасить лончер, але той все одно вбиває движок-нащадка «з ноги» (FN-007).
- **Урок:** «graceful shutdown» на Windows треба доводити для КОЖНОГО рівня дерева процесів; єдиний надійний доказ — банер збереження від найглибшого нащадка.
- **Зміна:** у харнесі CTRL_BREAK-шлях + перевірка `[qtier] HEAT_FILE saved`; прогалина задокументована як upstream-issue. → **PB-072**

### LL-010 | 2026-09-22 | Зовнішнє AI-рев'ю помиляється тим самим способом, що і ти
- **Контекст:** рев'ю іншої моделі (1540ae0) на нашому Phase 0.
- **Що сталося:** рев'ю зловило мою реальну помилку (LL-005), але саме приплюнуло qwen36 чужу змінну COLI_TEMP з вигаданим сидом — та сама плутанина рушіїв.
- **Урок:** рев'юер і автор хиблять кореляційно (спільні сліпі зони); одна перевірка не самодостатня.
- **Зміна:** тристороння верифікація зовнішніх рев'ю: твердження → мій grep по коду → друга незалежна модель; записано в процес. → **PB-073**

### LL-011 | 2026-09-22 | `cmd | tail` буферизує — логуй у файл напряму
- **Контекст:** моніторинг фонового бенчмарка через пайп у tail.
- **Що сталося:** вивід з'явився лише після завершення задачі; стежити за прогресом було неможливо.
- **Урок:** для фонових задач пишіть stdout одразу у файл (перенаправлення), а не через буферизований пайп.
- **Зміна:** bench-виклики пишуть `*_stdout.txt` напряму; моніторинг — по артефактах на диску.

### LL-012 | 2026-09-22 | Шукай proof-лінію ДО вердикту «фічі нема»
- **Контекст:** Phase 6 — я зробив висновок «KV-reuse не працює взагалі» без пошуку діагностичного перемикача.
- **Що сталося:** незалежне рев'ю (Opus) за п'ять хвилин знайшло документований `COLI_PREFIX_LOG=1`, який друкує `[PREFIX] reusing N of M` — доказ-рядок, створений саме «to distinguish "not faster" from "reuse is not wired up"». Діагноз змінився з «механізм мертвий» на «механізм працює, API не дотягується»; заодно виправилась атрибуція FN-008 і виявився методологічний баг мого зонда.
- **Урок:** перед негативним вердиктом про фічу — grep вихідників на її діагностику/логування та документацію ENV-перемикачів; і проганяй висновок незалежним рев'юером.
- **Зміна:** COLI_PREFIX_LOG=1 тепер у kv_reuse_test.py за замовчуванням; правило «proof-лінія перед вердиктом» додане до дисципліни (продовження PB-069/PB-073).
